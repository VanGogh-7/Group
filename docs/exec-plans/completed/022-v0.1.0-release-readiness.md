## Goal

Complete the locally provable preparation for an initial `0.1.0` crates.io
release of all eight workspace crates: publishable metadata and portable
dual-license packaging, registry-usable internal dependency metadata, locally
validated least-privilege CI workflow source, SQLite benchmark teardown
isolation, safe production logging guidance for the pinned Genai and rmcp
adapters, and reproducible local package inspection and later publication
procedures.

Completion of this Plan proves only bounded local release preparation. It does
not establish complete release readiness or CI success, and it does not
authorize a commit, push, tag, registry publication, or release. A clean,
committed release-candidate package gate, the first successful hosted CI run,
tag preparation, crates.io publication and index verification, and fresh
registry consumer verification remain later blockers behind separate
commit/push/release authorization.

## Non-goals

- Change Runtime, durable execution, Model, Tool, adapter, or Prebuilt public
  API behavior.
- Change checkpoint formats, Codec identity, migrations, durable lineage, or
  database behavior.
- Upgrade, downgrade, add, vendor, patch, or otherwise change third-party
  dependencies.
- Stabilize the experimental Genai, MCP, or Prebuilt public surfaces.
- Publish any crate, run `cargo publish`, reserve a crate name, create a tag,
  create a GitHub Release, or claim that `0.1.0` is released.
- Create a Git commit or push any branch, tag, package, or documentation.
- Run the clean, committed release-candidate package gate, prepare release
  tags, or perform hosted-CI, registry-index, or fresh-consumer release gates.
- Use a live Model Provider, remote MCP Server, provider credential, or
  quota-consuming test.
- Redesign the repository Harness or add release automation beyond the
  minimal CI and documented manual release procedure in scope.

## Proposed design

### Publishable metadata and dependency graph

Centralize shared release metadata in `[workspace.package]` where Cargo
supports inheritance, and inherit it in every crate. At minimum, every package
must expose an accurate description, license, repository, homepage, README,
edition, version, and effective MSRV. Use the repository URL
`https://github.com/VanGogh-7/Group` and keep crate-specific descriptions.
Add only accurate, release-relevant optional metadata if package diagnostics
show it is useful; do not invent unsupported capabilities.

Add `version = "0.1.0"` alongside `path` for every internal edge:

| Package | Internal normal dependencies | Internal dev-dependencies |
| --- | --- | --- |
| `group-agent-core` | none | none |
| `group-agent-model` | none | `group-agent-core` |
| `group-agent-tool` | `group-agent-model` | `group-agent-core` |
| `group-agent-checkpoint-sqlite` | `group-agent-core` | none |
| `group-agent-observability-tokio` | `group-agent-core` | none |
| `group-agent-genai` | `group-agent-model` | `group-agent-core` |
| `group-agent-mcp` | `group-agent-model`, `group-agent-tool` | `group-agent-core` |
| `group-agent-prebuilt` | `group-agent-core`, `group-agent-model`, `group-agent-tool` | none |

Do not change third-party requirements or features. Regenerate `Cargo.lock`
only if Cargo requires a mechanical lockfile normalization after manifest
changes; inspect and explain any lockfile diff rather than accepting dependency
version movement.

### Minimal CI

Add one narrowly scoped GitHub Actions workflow for pushes and pull requests.
Set workflow permissions to `contents: read`, disable checkout credential
persistence, avoid `pull_request_target`, services, deployment environments,
release permissions, provider secrets, and write tokens, and pin actions to
reviewed immutable revisions.

Use the repository entrypoints as the executable contract:

- run `./scripts/verify full` on Rust 1.88 for the complete workspace;
- install Rust 1.85 and 1.88 and run `./scripts/verify msrv` for the layered
  compiler floor.

Exact job factoring, runner concurrency, and safe dependency caching are
low-risk implementation details. CI must remain small, make the two gates
visible, and not copy the command bodies from `scripts/verify` into YAML.
This slice may add and locally validate only the workflow source. Neither the
slice nor Plan completion may call CI established or remove the hosted-run
blocker; that requires a successful GitHub-hosted run after separately
authorized commit and push operations.

### SQLite benchmark timing boundary

Keep database creation, seed execution, and fork-head creation in Criterion's
unmeasured setup. Keep restart connect, migration, and one-node branch resume
in the measured routine. Retain the temporary directory as batched input (or
otherwise return ownership past Criterion's timing stop) so database teardown
happens only after the measured interval. Validate cleanup and ownership; do
not leak the directory or weaken the benchmark assertion.

### Production logging guidance

Make one authoritative production logging section, linked from the README and
both adapter documents, that is actionable for `tracing` users:

- start from conservative upstream directives that disable `genai` and `rmcp`
  targets in production unless an application has audited and sanitized them;
- distinguish safe Group-owned default formatting from deliberate
  `Error::source()` traversal and from upstream dependency events;
- name payload classes that must be filtered, including prompts/messages,
  Tool arguments/results, raw HTTP/MCP data, headers, environment values,
  executable arguments, response IDs, and credentials;
- explain that raising upstream target levels is an application-level,
  environment-specific opt-in and must not be enabled merely to obtain Group
  lifecycle diagnostics;
- provide a copyable least-privilege filter example and a review checklist,
  validated against the pinned `genai` 0.6.5 and `rmcp` 2.2.0 source before it
  is documented.

Documentation changes must not claim Group can redact events emitted directly
by upstream crates or sanitize an already-formatted full source chain.

### Package preflight and publication boundary

Add one authoritative release runbook and link it from repository navigation.
It must separate these phases:

1. **Dirty local package preflight in this Plan.** Generate all eight local
   archives without publishing, inspect `cargo package --list`, extract each
   `.crate` into a fresh temporary directory, and inspect the normalized
   manifest and complete contents. Before using `--allow-dirty`, capture the
   complete authorized dirty state and diff, including every tracked,
   untracked, staged, and unstaged change relevant to packaging rather than
   naming only `docs/quality.md`. Record the exact exception set beside the
   package evidence. This is diagnostic evidence for the authorized working
   tree and is never a clean release-candidate package gate. Dependent packages
   may require archive generation without build verification until their
   internal dependencies exist on crates.io.
2. **Clean committed release-candidate gate in a separately authorized
   commit/push operation.** From the exact clean candidate commit, regenerate
   and inspect all eight archives without `--allow-dirty`, run the required
   verification, and obtain a successful hosted CI run. Only that later gate
   can establish clean-candidate package evidence and hosted CI success.
3. **Final crates.io-backed verification in a separately authorized release
   operation.** Recheck exact-name availability and the clean candidate,
   prepare the tag, then publish one crate at a time. After each dependency
   layer, wait for crates.io/index availability and prove that the exact
   `0.1.0` dependency resolves from the registry before packaging or publishing
   its dependents. After all eight are indexed, verify exact-version
   consumption from a fresh temporary consumer.

The only allowed publication order is:

```text
group-agent-core
  -> group-agent-model
  -> group-agent-tool
  -> group-agent-checkpoint-sqlite
  -> group-agent-observability-tokio
  -> group-agent-genai
  -> group-agent-mcp
  -> group-agent-prebuilt
```

This order is intentionally deterministic even where dependency-independent
crates could be reordered. An index timeout, ownership/name conflict, package
rejection, checksum mismatch, missing dependency, or exact-version consumer
failure stops the release. Do not skip ahead, retry publication blindly, or
publish a dependent crate against an unconfirmed index state. Actual ordered
publication requires a new explicit authorization and is not a slice of this
Plan.

### Portable license packaging

Create canonical root `LICENSE-MIT` and `LICENSE-APACHE` regular files, then
place full-text regular-file copies of both files in every crate root:

- `crates/group-agent-core`;
- `crates/group-agent-model`;
- `crates/group-agent-tool`;
- `crates/group-agent-checkpoint-sqlite`;
- `crates/group-agent-observability-tokio`;
- `crates/group-agent-genai`;
- `crates/group-agent-mcp`;
- `crates/group-agent-prebuilt`.

Do not use symlinks or parent-path packaging assumptions. Verify regular-file
type, exact byte equality, and equal cryptographic hashes from every
package-local copy to its canonical root file, then inspect every generated
archive to prove that both full texts are present and equal to the canonical
files. This controlled duplication is required for Windows/Linux portability:
an isolated Cargo probe established that inherited SPDX/readme metadata and
parent include paths do not place root license files in child package archives.
